    Our secure-user-mgt framework is designed to support software development
    teams that want enterprise-grade security discipline without enterprise
    tooling complexity and expense. It is designed to provide:

    - secure onboarding and offboarding of contributors
    - tracking of user metadata, with a focus on making it easy to revoke any
      tracked credential 
    - succession: no single key-holder's absence can freeze the 
      organization's ability to continue operations
    - expiry tracking with scheduled reminders, so that an expiring token 
      (e.g., npm tokens) triggers a warning _before_ releases fail 
      due to  publishing lock outs.  

    Open source projects are an ideal first use case. Volunteers often 
    roll on and off teams, and handling the on/off-boarding  manually 
    is a time sink. Moreover, leaving a credential of a 
    no-longer-participating team member can leave the 
    organization open to loss if the parting is not amicable.

*** Please give a detailed description of the project.

  secure-user-mgt is a set of automated procedures and policies, with scripts,
  for a small organization that cannot afford an IT department. It covers
  three needs:

  - Onboarding and offboarding members. A new member submits their details
    through a script, which proposes the change on a branch of the registry
    for an approver to merge. When someone leaves, a script lists everything
    that person held and prints what to revoke on each platform.
  - Tracking credentials. A registry, which is a plain git repository of one
    small file per member, records each token issued to each member with its
    expiry date, so that nothing is forgotten when someone leaves. A report
    lists what is held and what is due.
  - Succession. Two named roles, an OWNER (usually the founder) and a DEPUTY,
    hold the keys. A written procedure covers handover when one of them
    leaves, and a second, stronger procedure rebuilds access to the OWNER's
    account from three of five secret shares if the OWNER cannot be reached.
    Which procedure to use, and when, is documented.

  The shared secrets live in a Bitwarden organization with separate
  collections for operations and finance. The scripts read secrets only for
  the operations collection, and never read the finance collection. Platforms
  that issue tokens are handled by small plugins, which anyone can write.

  Status: the design is complete and the implementation is under way. The
  first commit was on 2 November 2026. Scripts exist for onboarding, approval,
  developer onboarding, offboarding and reporting, and have been tested
  against a mock vault and run by hand by the OWNER against a real one. The
  package is not yet published to npm. Sample plugins are planned.

  Much of the code is written with AI assistance, from specifications that a
  person writes and reviews. We say so plainly because we know Conservancy's
  views on AI code generators.
